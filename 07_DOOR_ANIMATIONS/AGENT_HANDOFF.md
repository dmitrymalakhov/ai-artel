# Агенту: двери и проход персонажей

Подключи обе двери к существующему приложению вместе с 06_CHARACTER_ANIMATIONS. Сначала прочитай его AGENT_HANDOFF.md, затем эту инструкцию и manifest.json. Сохрани существующий движок и реальные задачи персонажей.

## Подключение графики

1. Если офис использует единый фон, подключи scene/character_free_doors_open.png вместо старого character_free_restoration_plate.png. Старый фон содержит закрытые двери: поверх него открытие не создаст прохода. Исходный файл не удаляй. Новый фон меняет только две области из manifest.scene.editedRegions. Если персонажи нарисованы и на фоне приложения, используй вариант без персонажей.
2. Если сцена модульная, убери старые статичные створки в этих двух входах, сохрани стены и открытые проходы. Не используй полный фон поверх существующей мебели.
3. Загружай атласы и координаты кадров из doors/. Размеры двух дверей различаются. scenePosition — левый верхний угол кадра на исходной сцене; anchor — привязка внутри него. С origin=(0,0) используй scenePosition, с нормализованным origin=anchor/frameSize — мировую позицию scenePosition+anchor. Не прибавляй anchor дважды.
4. Фон рисуется позади актёров. Дверную створку сортируй относительно точки ног по depthY; актёр в комнате за створкой, актёр в коридоре перед ней. frame_foreground рисуется перед актёрами в зоне входа, чтобы косяки и направляющая закрывали тело физически правдоподобно. Не создавай коллизию по всему прозрачному прямоугольнику спрайта.
5. Рисуй nearest-neighbor. Если сцена не 1254×1254, пересчитай позиции, пути, depthY, clearance и размеры одним масштабом. waypoints — стартовые точки ног для этой сцены, а не универсальные координаты приложения. Согласуй радиус тела с шириной прохода; для узкого кабинета придерживайся одного человека за раз.

## Когда открывать

Открывай конкретную дверь, если актуальный путь персонажа пересекает её проём: из коридора в кабинет/переговорную либо обратно. Соседний проход мимо двери не является запросом. Для кабинета учитывай уже существующие права доступа приложения до резервирования прохода. Не придумывай новый запрет на вход по цвету одежды.

Перед проёмом поставь персонажа в очередь на точке ожидания. Остановившийся персонаж показывает idle с направлением к двери. Запрос открывает дверь; пока открытие не закончено, движение через неё запрещено. По завершении открытия выдай разрешение первому ожидающему и включи walk_up при движении в комнату, walk_down при выходе на исходной сцене. Если проект повёрнут/перестроен, направление выбирай по фактическому вектору движения.

Вход в комнату не должен сам по себе запускать work или seated_talk: после прохода продолжай актуальный маршрут к столу/сиденью, затем обычную посадку и занятие из инструкции персонажей. После выхода продолжай назначенную задачу. Ключи walk/idle принадлежат персонажу, ключи open/close — объекту двери.

## Состояния двери

| Состояние | Отображение | Проход |
| --- | --- | --- |
| closed | Кадр 0, неподвижно | Заблокирован |
| opening | Кадры 0→7, один раз | Заблокирован до завершения всей последовательности |
| open | Кадр 7, неподвижно | Разрешён выданному владельцу прохода |
| closing | Кадры 7→0, один раз | Новые проходы заблокированы |

Длительности бери из manifest. Анимации opening/closing не зацикливать и не перезапускать на каждом обновлении. events.passage_ready содержит phase=completion: даже показ последнего кадра не означает, что его выдержка уже закончилась. Контроллер даёт разрешение после полного открытия.

У двери одна FIFO-очередь для обоих направлений. Запросы одного персонажа не дублируются. Зарезервированный проход не равен праву войти в занятое кресло; мебель сохраняет отдельное резервирование. Если в реальной сцене нельзя разойтись снаружи, настрой отдельные безопасные точки ожидания по сторонам, чтобы очередь не складывалась в одном месте.

Не освобождай проход, когда персонаж только пересёк линию двери. Дождись, пока весь его коллизионный круг/капсула покинет clearance с запасом. Затем освободи разрешение и выдай его следующему. Для демо используются конечные waypoints; в приложении нужна проверка фактической геометрии тела.

## Когда закрывать и как прерывать

- Закрывай только при пустой очереди, отсутствии активного прохода, персонажей в зоне безопасности и физических препятствий. Выдержи autoCloseDelayMs после освобождения зоны.
- Если новый запрос или препятствие появляется во время closing, разверни в opening с текущего кадра, без скачка в кадр 0. Не выдавай новое разрешение до полного открытия.
- Если задачу отменили до прохода, убери её запрос из очереди. Уже проходящего человека сначала доведи к безопасной стороне, затем освободи проход и меняй маршрут.
- Если человека удалили, отменили сцену или сменили этаж, очисти его запрос, активное разрешение и датчики. Не оставляй вечную блокировку.
- Пауза игры останавливает таймеры и анимации. После задержки кадра обрабатывай завершения по времени и только один раз; не пропускай освобождение и выдачу разрешения.
- Не ставь автоматический таймаут, который закрывает дверь через застрявшего персонажа. Исправь его путь либо безопасно выведи из зоны, прежде чем освобождать проход.

## Готовый JavaScript-контроллер

tools/door-controller.mjs экспортирует DoorController. Передай ему конфигурацию соответствующей двери из manifest.doors и необязательные hooks: onStateChange, onPassabilityChange, onTraversalGranted, onTraversalReleased. В начале установи коллизию закрытого проёма явно: конструктор не вызывает hooks.

- request(actorId, 'corridor'|'room') — запрос пересечения с указанной стороны; сторона назначения противоположная.
- tick(deltaMs) — игровое время; frameIndex задаёт текущую позу. При паузе не вызывать либо передавать 0.
- setNearby(actorId, present) — датчик безопасности возле проёма, не автоматическое назначение маршрута.
- setObstruction(id, present) — тело/объект, мешающее закрытию. Удаляй из датчика после выхода.
- active.actorId или onTraversalGranted — разрешение конкретному человеку начать пересечение. Одного passable=true недостаточно для всех ожидающих.
- release(actorId) — завершение прохода после полного выхода тела; возвращает false для чужого/повторного освобождения.
- cancel(actorId) — отмена только ожидающего запроса; активный человек сначала завершает выход из зоны.
- removeActor(actorId) — уборка при фактическом удалении персонажа, не замена безопасному выходу живого актёра.

Контроллер не двигает персонажей и не строит пути. Перенеси эту логику в существующий движок, если приложение не JavaScript. Не копируй просмотр index.html как архитектуру всего приложения; его движение задано только для демонстрации ассетов.

## Проверка в приложении

Проверь обе двери: вход и выход, остановку перед закрытой створкой, одновременные запросы с двух сторон, очередь, отмену задачи, удаление ожидающего и проходящего, новое приближение во время закрытия, долгое препятствие, паузу и низкую частоту кадров. Дверь не должна закрываться на тело, актёр — проходить через закрытую дверь, новая створка — дублировать старую, косяки — исчезать, а персонаж — терять задачу.

Покажи итоговую сцену и перечисли привязки, коллизии и реальные события проекта, которыми управляются двери. Превью и проверки пакета подтверждают готовность ассетов и примерного контроллера; интеграция в целевой движок требует отдельного запуска приложения.
